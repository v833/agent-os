# 团队 Bot 协同工作流

除了单个 Bot 独立写代码，ThreadPilot 最强大的能力在于支持配置一支**各司其职的多 Bot 产研团队**。

通过内置的团队交接单（Collaboration）、产品方案确认卡与隔离 QA 质量门禁，多个 Bot 能在飞书群中自主推进“需求澄清 → 方案确认 → 编码开发 → 快照验收”的完整闭环。

---

## 一、团队预置角色与职责分工

在 `config/bots.json` 中，你可以定义多台不同职责的成员：

### 1. CEO 助理 (`ceo-assistant` - Team Leader)
- **职责**：团队负责人与编排者，负责宏观目标理解、任务拆解与组织派发，最终向真人收口汇报。
- **独有特权**：**全团队中唯一允许调用 `dispatch_task` 工具的成员**。其他成员如果试图调用派发工具会被系统鉴权拒绝，防止 Bot 之间无序互相派发陷入混乱。
- **适用场景**：复合型、跨阶段需求（如“为系统新增微信登录模块”、“重构数据层并补全单元测试”），直接找 CEO 助理。

### 2. 产品经理 (`product`)
- **职责**：需求深度澄清与方案设计，将模糊诉求转化为规格说明（Spec）与实现任务清单（Tickets）。
- **专业技能**：自带需求澄清问卷（`grill-me`）、规范化生成（`to-spec` / `to-tickets`）与飞书云文档自动建档能力。
- **适用场景**：业务边界模糊、需要先定产品方案与交互原型时。

### 3. 开发工程师 (`developer`)
- **职责**：工程实现、功能编码、依赖维护与本地测试编写。
- **执行特性**：聚焦代码本身，基于产品经理交付的明确方案或 CEO 助理指派的技术任务快速编写代码。
- **适用场景**：明确的 Bug 修复、接口开发、重构或具体特性编写。

### 4. QA 质量验收工程师 (`qa`)
- **职责**：质量把关与门禁验收。
- **核心安全机制**：**QA 绝不在开发工程师正在编辑的活动目录下直接跑测试**，而是由系统自动克隆一份**隔离工作区快照**，在隔离环境中运行构建与自动化测试。
- **适用场景**：代码交付前的质量把关、复杂回归缺陷复现。

## 二、产品方案交付与发起人确认闭环

产品经理生成方案后，有两种交付形态（二者互斥，由 `config/bots.json` 的 `defaultProductDeliveryMode` 决定）：

1. **飞书云文档模式 (`lark-doc`)**：产品经理自动在你的飞书知识库中新建一篇云文档，内置完整的产品说明与实现 Tickets，并在群里给出文档链接。
2. **本地文件模式 (`local`)**：方案以 Markdown 文件形式落盘到本地工作区的 `.scratch/<feature>/spec.md` 和 `issues/` 目录。

### 发起人确认卡机制
方案就绪后，群内会弹出**方案确认交互卡片**：
- **发起人鉴权**：只有本次任务的真人发起人点击「确认」才有效，避免旁人误操作。
- **两种走向**：
  - **直接确认**：标记方案已就绪，流程结束。
  - **确认并交给 Leader**：系统自动将方案作为正式团队任务派发给 CEO 助理，由其调用 `dispatch_task` 指派合适的开发工程师开始写代码。

### 飞书云文档评审评论回路
如果方案采用飞书云文档交付，你在阅读文档时，可以直接在正文划词并 **`@产品经理` 发表评论**（例如：“*密码长度需要支持 16 位*”）：
1. ThreadPilot 收到 `drive.notice.comment_add_v1` 事件，根据文档 Token 自动找回当时的产品会话；
2. 恢复该产品经理的 CLI 会话，精确修改云文档正文；
3. 将修改摘要自动回复到该条评论下方。
4. 多个评论自动串行排队处理，评论是否点击「解决」完全由你决定，系统不会强行关闭你的评审评论。

## 三、QA 质量闸门与快照三态闭环

当开发工程师完成代码后（若配置了 `"reviewBy": "qa"`），系统会触发 QA Gate 质量门禁：

```text
[开发工程师完成编码]
       │
       ▼
[系统自动创建工作区隔离快照] ──► 计算并固定工作树稳定 Revision
       │
       ▼
[QA 工程师在快照中执行构建与测试]
       │
       ▼
 ┌───────────── 三态质量结论判定 ─────────────┐
 │                                           │
 ▼                                           ▼
[pass: 验证通过]                     [changes_requested: 需返工]
 结束交付链路，通知真人               退回开发修复缺陷，随后生成新快照复审
                                             │
                                             ▼
                                     [blocked: 严重阻塞]
                                     升级 Team Leader 介入处理环境/权限
```

| 结论代码 | 含义 | 系统后续动作 |
| :--- | :--- | :--- |
| `pass` | 审查完全通过 | 结束开发交付链路，向发起人汇报最终成果。 |
| `changes_requested` | 存在缺陷需要返工 | 自动携带测试失败日志退回给开发工程师，修复后重新生成快照复测。 |
| `blocked` | 严重阻塞（缺少依赖/权限不足） | 停止自动重试，升级给 Team Leader 介入排查环境或协议问题。 |

> **防伪校验**：QA 会校验报告中的 revision 与快照目录实际 revision 是否完全一致。如果不一致，判定为 `blocked`，杜绝“审查版本与交付版本脱节”的伪测试。

## 四、团队协作全景流程示例

```text
[真人用户在飞书话题提需求]
           │
           ▼
     [CEO 助理] ──── 理解目标并规划路线
           │
           ├─► [产品经理] ──── 澄清歧义、设计方案、交付飞书云文档
           │         │
           │         ▼
           │   (弹出确认卡，真人用户点击「确认方案并交给 Leader」)
           │         │
           ├─► [开发工程师] ── 编写业务代码与单元测试
           │         │
           │         ▼
           └─► [QA 工程师] ─── 提取快照物化环境，执行回归测试
                     │
                     ▼
             (通过 pass 后，由 CEO 助理汇总结果并通知真人用户)
```

整个过程均在飞书同一个话题中推进，每一步流转都有卡片可查、可控、可停，实现团队级的高效自治研发。
